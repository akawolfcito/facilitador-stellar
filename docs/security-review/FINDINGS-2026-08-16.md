# Security findings, 2026-08-16

Found during security review preparation, before the documentation package was
written. Per the phase rules, nothing here has been fixed: findings are kept
separate from documentation work.

**No code was changed. One measurement script was run locally and deleted.**

---

## SR-01 — Every visitor shares one rate-limit bucket, and one visitor can be shown another's result

**Severity: MEDIUM.** **Status: OPEN, not fixed.**
**Component:** `x402seek-web` (`src/server.ts`), and by inheritance
`apps/demo-buyer` (`src/app.ts`).

### What is wrong

`x402seek-web` builds Fastify as `Fastify({ logger: false, bodyLimit: 2 * 1024 })`.
`trustProxy` is not set, so it defaults to `false`, so `request.ip` returns the
socket peer address. Behind Railway's edge that peer is Railway, not the visitor.

`clientKeyFor(request.ip)` therefore returns **the same key for every visitor on
the internet**.

### Measured, not inferred

Two Fastify instances, one built exactly as deployed and one with `trustProxy`
enabled, each asked for `request.ip` with different `x-forwarded-for` values:

```
as deployed   visitor A -> 127.0.0.1     visitor B -> 127.0.0.1     SAME BUCKET
trustProxy    visitor A -> 203.0.113.7   visitor B -> 198.51.100.9  distinct
```

Railway is confirmed to be a separate hop in production: responses carry
`server: railway-hikari` and `x-railway-edge: atl1`.

### Consequences

1. **Cross-visitor result disclosure, and a false "settled" message.** The demo
   buyer's 30-second duplicate guard matches on the bucket. With one shared
   bucket, a second visitor clicking within 30 seconds of a first receives the
   *first visitor's* stored response: their transaction hash, and the seller's
   summary of **the text the first visitor typed**. The second visitor is told
   "Payment settled" having caused no payment. This is the part that makes it
   MEDIUM rather than LOW: it is a correctness failure and a small confidentiality
   leak of another user's input, and it needs no attacker — two people clicking
   near each other is enough.

2. **The per-visitor limit is a global limit.** Three demo payments per hour,
   for the entire site rather than per person. Anyone can spend the world's three
   and deny the demo to every reviewer for an hour, deliberately or by accident.

3. **The same blindness exists on the facilitator.** `apps/facilitator/src/app.ts`
   reads `config.trustProxy ?? false` and `TRUST_PROXY` was never set on the
   deployed service, so its settle, verify and search limiters also bucket every
   caller together. That is availability only: one noisy seller can throttle all
   sellers. No spend consequence.

### What is *not* affected

Worth stating precisely, because the blast radius is bounded and the money
controls are intact:

- No payment invariant is weakened. The caller still supplies no `payTo`, amount,
  asset, network, resource or facilitator, and the two-layer live-402 boundary is
  untouched.
- The **daily budget still holds**: 150 payments and 0.15 USDC per UTC day are
  enforced in the persistent ledger and are global by design, so the worst case
  is still bounded at 0.15 USDC per day.
- Settlement, the facilitator signer and the spend ledger are unaffected.
- `apps/demo-buyer` sets `trustProxy: false` **correctly**: it sits on Railway's
  private network with one peer, so trusting a forwarded header there would be
  the bug. Its `clientKey` mechanism is the right design; it is being fed a
  useless value by the layer above.

### Why the earlier fix did not catch it

Commits `dcb9e75` and `d998705` introduced `clientKey` precisely to stop every
visitor arriving as one bucket at the demo buyer. That reasoning was right and
the mechanism is right. It moved the derivation to "where a visitor still
exists", and then derived it from a field that, behind a proxy, does not contain
the visitor either. The tests pass because `app.inject({ remoteAddress })` sets
the socket address directly, which is exactly the condition production does not
have. A test can only catch this by asserting on `x-forwarded-for`.

### Smallest proposed fix

Two lines and one test, in `x402seek-web`:

1. `Fastify({ ..., trustProxy: 1 })` — trust exactly one hop, Railway's edge, so
   the rightmost `x-forwarded-for` entry wins and a client-supplied header cannot
   spoof a bucket.
2. A test that drives the route with `headers: { "x-forwarded-for": ... }` rather
   than `remoteAddress`, asserting two forwarded addresses land in different
   buckets and that a caller-supplied header cannot impersonate a third.

Separately, and as a smaller decision: set `TRUST_PROXY=1` on the deployed
facilitator, whose code already supports it.

**Not applied in this pass, by instruction.**

## SR-02 — Metrics token compared with a non-constant-time equality

**Severity: INFORMATIONAL.** **Status: OPEN, not fixed.**
**Component:** `apps/demo-buyer/src/app.ts`.

`if (offered !== \`Bearer ${config.metricsToken}\`)` short-circuits on the first
differing byte, so the comparison time leaks a prefix match.

Exploitability here is close to zero: the route is on a service with no public
domain, reachable only from inside the Railway project, and a wrong token returns
404 rather than 401 so the endpoint does not advertise itself. Recorded because
an auditor will notice it and because `timingSafeEqual` costs one line.

The facilitator's equivalent guard should be checked at the same time.

## Not findings

Examined and found correct, recorded so the eventual audit does not re-derive
them:

- The demo buyer has no public domain. `demo-buyer.testnet.x402seek.xyz` does not
  resolve, verified from outside.
- The ownership verifier validates **every** resolved address before connecting
  and pins the validated one, so the DNS-rebinding window is closed.
- The browser receives no key: `app.js` contains no `S…` strkey, no
  `DEMO_BUYER_SECRET`, no `METRICS_TOKEN`.
- The demo buyer and the facilitator hold different secrets in different Railway
  services.
- Domain verification is never awaited on the settlement path.
- The spend ledger reserves before signing and never releases after signing.

---

## Recommendation

Fix SR-01 before the documentation package is written, or at least before it is
handed to a reviewer. A package that describes a per-visitor rate limit which is
not per-visitor would be describing a system that does not exist, and that is a
worse outcome than the defect itself.

SR-02 can ride along with it or wait for the audit.
